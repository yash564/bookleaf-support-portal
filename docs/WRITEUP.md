# Write-up — BookLeaf Author Support Portal

**What I prioritised.** The brief weights AI integration and architecture at 50% combined, so I spent the budget there: a clean layered FastAPI service with typed contracts and one error envelope, and an AI package designed the way I would ship it in production rather than as a demo call. Concretely: classification and priority in a single structured-output call that runs *after* the ticket is committed; drafts grounded in both the knowledge base and the author's real royalty rows (pending amount, last payout, computed next payout date, threshold rollover) so the reply can be specific the way BookLeaf's tone guide demands; a cached draft per ticket with an explicit regenerate; prompt caching for the static policy block; a circuit breaker and a rule-based fallback so the ticket flow never depends on Anthropic being up; and a token ledger so "cost-aware" is measurable in the admin UI rather than a claim. The second priority was the ticket lifecycle feeling real for both sides — urgency-first queue, assignment and internal notes, override audit, reopen-on-reply, live updates — and handling the dataset's edge cases (in-production books, sub-threshold pending, zero payouts, empty states) explicitly.

**Trade-offs.** I chose a split deploy (Vercel + Render + Neon) over a single Next.js full-stack app because a genuinely separate REST API with generated OpenAPI is what the evaluation asks for, at the cost of a second service and CORS. Server-Sent Events over WebSockets: one-directional updates are all the product needs, SSE works through ordinary HTTP proxies, and the "signal then refetch" pattern keeps one serialisation path; the in-memory broker is the honest single-instance choice with a documented Redis swap. Haiku 5.5 over a larger model: triage and support drafting are routine, it is ~10× cheaper than the previous Haiku, and its 512-token cache minimum means the knowledge-base block actually caches. A hand-rolled UI kit instead of a component library, because the brief values explainable code over polish. JWT in localStorage and metadata-only attachments were deliberate scope cuts, documented as limitations.

**Evolving it into production.** Platform: Redis pub/sub for realtime across instances, background jobs (classification, future email/WhatsApp notifications) on a queue instead of in-process tasks, httpOnly refresh tokens, rate limiting, audit log table, OpenTelemetry tracing with the request id. Product: author-side notifications on reply, SLA timers per priority surfaced in the queue, canned-response library seeded from accepted AI drafts, attachments with real upload and multimodal review of defect photos, a payouts table so "next payout" comes from scheduled runs rather than the calendar. AI: treat every admin edit to a draft and every override as a label, build a golden set, and gate prompt changes on measured classification accuracy and draft acceptance rate per `PROMPT_VERSION`; add per-category few-shot selection from *approved* real replies; consider escalating only low-confidence classifications to a larger model. The layering is already in place for each of these — routers, services, repositories and the AI package change independently.
